两个进程：同一套代码，为什么分开跑、隔离到哪一步

机制：进程与资源（后端框架 0004 第 2.1、2.5、6.1、6.4、10.2 节）。例子：张三的回答正在生成，后台进程突然崩了。

这一页想让你讲得出：两个进程各开了什么；后台进程挂了，哪些功能照常、哪些停住、怎么恢复；分开以后隔离到哪一步，哪些东西仍然是共用的。 框架 = 你负责的 0004；M01 = 会话（嘉敏）；M04 = Agent 配置与发布（蕴颐）。

① 先分清四对词

同一套代码 ≠ 同一个进程

代码
两个进程装的是同一套后端代码：平台内核 + 九个业务模块，一个都不少。
进程
区别只在启动时开了哪些宿主职责：请求进程开 HTTP 端口、不领任务；后台进程领任务、跑定时和跟随器，不开业务端口（只留健康检查和指标）。
代码在，不代表会运行。请求进程里也有「领任务」的代码，只是没有启动它。

线程 ≠ 数据库连接

线程
执行代码的工人。每个进程有好几个线程池（页面请求、执行池、事件监听……）。
连接
和数据库之间的一条通道。每个进程一个共享连接池，线程要查库时借一条，用完就还。
请求进程有 200 个页面请求线程，但只有 10–20 条连接。连接数按「数据库同时要执行多少查询」配，和用户数无关。

分开 ≠ 完全隔离

分开了的
内存、线程、连接池、崩溃。后台进程卡死、占满自己的连接，借不走请求进程的。
还共用的
同一个数据库：CPU、磁盘、行锁。后台进程的事务锁住一行，请求进程要改同一行，照样要等（最多等 20 秒就报错）。
隔离的是「进程挂了」，不是「数据库忙了」。

后台进程 ≠ 评估执行器

后台进程
Java，装全部模块，直接连数据库领任务。
评估执行器
Python，不装模块、不连数据库，只调请求进程上的内部接口：由请求进程代它领评估任务、续租；它跑被测、模拟用户、评分会话，把结果交回自进化模块。
所以「请求进程不领任务」有一个例外：评估任务由请求进程代评估执行器领取。
用到的三个基础概念（不熟就点开）

进程：一个运行中的程序，有自己的内存和线程。两个进程之间不共享内存，要交流只能经数据库或网络。这里的两个进程是两个 Java 程序（两个 JVM）。

Spring 装配：启动时，Spring 按配置把各模块的对象创建好、互相接上。两个进程的启动入口不同，开启的宿主组件就不同（比如只有请求进程启动 HTTP 服务器）。

租约：领到任务的进程每 20 秒续一次「我还在做」，60 秒没续就算它没了，别人可以接手（A6 讲）。

④ 为什么这样分 每条都是「不这样会坏在哪」

1. 为什么不放在一个进程里？

放在一起：后台的长任务出了问题（卡死、内存涨爆、进程崩），页面也一起挂；想多加几个跑任务的实例，只能连页面服务一起加。

分开后：后台进程崩了，登录、看历史、管理页面照常（第 3–4 步）；后台进程可以单独加实例。

2. 为什么不干脆拆成九个服务，每个模块一个？

拆成九个服务：模块之间的调用都变成网络调用，要多处理超时、重试、部署和运维九套东西，团队现在承担不起。

现在模块之间是进程内的 Java 接口调用。接口按契约定义，以后真要拆，把调用换成远程适配器，调用方的写法不变（0004 第 2.4 节）。请求进程和后台进程之间本来就只靠任务表和事件交流，拆不拆都不用改。

3. 后台进程重启只要 30 秒，为什么张三的回答要停一分钟左右？（第 5–6 步）

重启后的进程是一个新的执行者。旧进程持有的跟随任务，租约还没到期，任务表还认为它在做；新进程必须等租约过期才能接手，不然可能出现两个跟随器。

对比：正常停机（比如发版）时，后台进程先停止领取，等进行中的任务 30 秒，结束不了的主动放弃租约，别人马上能接，不用等过期。

4. 既然重启也要等租约过期，为什么还建议部署两个后台进程？

恢复速度差不多，差别在会不会恢复。

只有一个：如果它起不来（机器坏了、反复崩），跟随器、应答通道、所有后台任务就一直停着。

有两个：一个没了，另一个的过期检查照常运行，租约一过期就接手，不依赖重启成功。RFC 把这一条列为缺点：后台进程是执行链路的单点（0004 第 10.2 节、Q4）。

5. 为什么评估执行器不直接连数据库？

RFC 的规定：它不装模块、不连数据库，只调内部接口；用哪个 Agent 版本、哪个评估账号，一律由自进化模块从评估记录里取，执行器改不了（0004 第 2.1 节）。

我的理解（RFC 没明说理由）：让它连库，就要在 Python 里再实现一遍任务表的领取、租约规则和权限判断，两套实现很容易不一致；不连库，规则只在 Java 这一边。

6. 为什么连接池这么小？用户多了不会不够吗？

连接按「数据库同时在执行多少查询」配。一次查询几毫秒，十几条连接每秒能服务上千次查询。

配太大：数据库同时处理的查询太多，反而都变慢；三个进程加起来很容易超过数据库允许的连接数。这也是每个进程只用一个连接池、不按模块各开一个的原因（0004 第 10.1 节）。

⑤ 它不保证什么

  • 不是完全隔离。两个进程共用一个数据库：后台进程的慢查询会拖慢数据库，后台进程的事务锁住的行，请求进程要改也得等（锁等待超时 20 秒）。
  • 只部署一个后台进程时，它是执行链路的单点。它挂了，进行中的回答停住、审批一直等、新执行不派发，直到它恢复。
  • 内存不共享。一个进程清了自己的缓存，另一个进程的缓存还在（停用账号后，其他请求进程最多 30 秒后才生效，B6 讲）。
  • 代码在不代表会运行。哪个进程跑什么，取决于启动时开了哪些宿主组件。配置错了（比如请求进程也开了领取），RFC 没有专门的启动检查拦住，要靠部署配置和评审。
  • 重启不等于马上恢复。崩溃后要等旧租约过期，跟随器才能被接手，大约一分钟。

⑥ 自测 先自己想，再点开

1. 只有一个后台进程，它挂了 2 分钟。这期间：张三能登录吗？能看历史对话吗？他正在看的回答会怎样？他能发一个新问题吗？

能登录、能看历史，这些都在请求进程里。正在看的回答停住不动（跟随器在后台进程里），DSH 那边其实还在跑。发新问题：应答通道断了，会话模块不派发新执行，页面提示「执行服务暂不可用」。

2. 同一时间，管理员点了「发布」。会怎样？

请求进程照常受理，事件登记、建任务都在请求进程里完成（A5 第 1–3 步），任务在任务表里排队。后台进程恢复后马上领走，因为这个任务没有被任何人持有，不用等租约。

3. 后台进程崩溃后 25 秒就重启好了，最后一次续租在崩溃前 10 秒。跟随任务什么时候被接手？

租约在最后一次续租后 60 秒到期，也就是崩溃后约 50 秒；之后下一次过期检查（每 10 秒一次）退回排队，再被领走。所以大约在崩溃后 50–60 秒，和重启快慢无关（只要重启比这快）。

4. 后台进程的 8 个 default 线程都在忙，连接也借光了。张三在页面上登录，会受影响吗？

一般不会。请求进程有自己的线程和连接池，后台进程借光的是它自己的。除非后台进程的事务正好锁着登录要改的那一行，或者把数据库本身拖慢了。

5. 「请求进程不领任务」有没有例外？

有。评估执行器不连数据库，它的评估任务由请求进程上的内部接口代它领取、续租。真正跑评估的是评估执行器自己。

出处：0004 第 2.1 节（三个进程各做什么、评估执行器的接入方式）、第 2.4 节（以后拆服务契约不变）、第 2.5 节（连接池大小、锁等待超时 20 秒）、第 3.4 节（租约、过期检查）、第 3.7 节第 1 条、第 5.2 节（逐字增量由后台进程推给请求进程）、第 6.1 节（后台进程关闭时的处理）、第 6.2 节（跟随器从会话模块记下的 DSH 序号接着跟、补缺口）、第 6.3 节（通道中断时不派发新执行、限时提问到时变「待回答」）、第 6.4 节（线程预算）、第 10.1 节、第 10.2 节（后台进程是单点、守护进程 30 秒内重启）。
示意，不是 RFC 定的：所有时间、ID、会话事件的序号和类型、DSH 进程编号。
我的理解，RFC 没明说：④ 第 5 条「评估执行器不连库的理由」；⑤ 第 4 条「请求进程误开了领取没有专门的启动检查」（RFC 只说任何一项与清单不一致启动失败，没说宿主职责开关怎么检查）。
