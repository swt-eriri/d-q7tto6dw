后台任务：谁来做、怎么排队、做到一半出事了谁接手

机制：任务表（后端框架 0004 第 3.4、3.5、3.6 节）。例子：「客服 Agent」连着发布两次，部署了两个后台进程。

接着 A5 讲：事件把任务建出来以后，任务表怎么保证「有人做、不撞车、按顺序、出事有人接」。 框架 = 你负责的 0004；M04 = Agent 配置与发布（蕴颐）。

① 先分清四对词

去重键 ≠ 串行键

去重键
防止同一件事建出两个任务。（任务类型，去重键）唯一，事件建的任务填事件 ID。
串行键
让不同的任务排队：同一个串行键同时只跑一个，并按提交顺序跑。
这一页里：两次发布是两个事件 → 两个不同的去重键 → 两个任务；但串行键都是 agent-publish:客服 → 排队。

租约 ≠ 运行时间上限

租约
「我还活着、还在做」的证明，60 秒有效，每 20 秒续一次。
运行时间
任务本身要做多久，和租约无关。只要一直续，跑 12 分钟也没问题。
租约过期的意思是「60 秒没人续了」，不是「任务跑太久了」。

代次 ≠ 尝试次数

代次
每领取一次加一，用来认人：续租、写结果都带「代次等于我领到的那一代」，对不上就说明任务已经被别人领走了。
尝试次数
也是每领取一次加一，用来止损：到了上限（默认 5 次）就不再重试，标「死信」并告警。
按现在的 RFC 两个数总是一样（都在领取时加一），只是用途的名字不同（⑤ 第 8 条）。

任务只建一次 ≠ 只执行一次

只建一次
靠去重键，任务表里只有一行。
执行
这一行可能被领取好几次：崩了被接手、卡住被接手。旧执行者发现自己失去资格之前，最长有 20 秒两个进程在做同一个任务。
所以任务处理器必须做到「重复执行也不出错」。这是模块的责任，框架替不了。
用到的四个基础概念（不熟就点开）

行锁：事务里用 SELECT … FOR UPDATE 读一行，就把这一行锁住，别的事务想改它要等到提交。加上 SKIP LOCKED，别的事务遇到被锁的行不等，直接跳过去找下一行。

条件更新：UPDATE … WHERE id = ? AND 代次 = 1。数据库会告诉你改到了几行：改到 1 行说明条件成立；改到 0 行说明条件已经不成立了（比如代次已经变成 2）。不用先查再改，也就不会被别人在中间插队。

唯一索引：某一列（或几列）的值在表里不能重复，重复插入或改成重复值时数据库直接报错。任务表有一列「运行中串行键」：只有状态是运行中时才有值，其余为空；空值不算重复。

数据库时间：租约的「到期时间」写在任务表里，用数据库的时钟算（UTC_TIMESTAMP(3)），不用各台机器自己的时钟，免得几台机器时间不一致。

③ 任务的几种结局

结局什么时候之后
成功处理器正常做完，带代次条件写结果成功写完成时间；30 天后清理
失败业务上明确做不了，比如发布校验时发现必要的 tool 缺失不重试。重试也是同样结果
重新排队（退避）暂时性的错误，比如 DSH 一时连不上按指数退避推迟「最早可领时间」再排队；下次领取尝试次数照样加一
死信尝试次数到了上限（默认 5）。反复把进程搞崩的任务也算：领取时就加一，不是做完才加告警，等人来看
已取消有人请求取消排队中的直接改成已取消；运行中的只做标记，处理器在续租时看到，找个安全的地方收尾（协作式取消，不强杀）

长任务池（DSH 跟随器、应答通道）不限尝试次数，改为「1 小时内被重新领取超过 10 次就告警」。

④ 同一张表还管的两件事 「只能由一个实例做的事」不选主，也落在任务表上

定时任务

每个后台进程每秒检查一遍定时规则（cron，按北京时间）。到点时，每个进程都去插一个任务，去重键是 cron:规则名:计划时间。两个进程都插，唯一约束只让一条成功。

例：身份模块的每日清理（0006）。两个后台进程在计划时间各插一次，表里只有 1 条。进程宕机期间错过的，恢复后最多补一次。（规则名和时间是示意。）

每个 DSH 进程一个应答者

每个 DSH 进程只能有一个连接负责回答问题和审批（A10 讲为什么）。做法：每个 DSH 进程一个长任务，去重键是 DSH 进程编号；租约保证同一时刻只有一个后台进程持有它。持有者退出，租约过期，别的后台进程接手、重连。

和发布任务用的是同一套领取、租约、代次，没有另写一套机制。

为什么不选主

选主就是「几个进程里选一个老大，只有它做这些事」。不选的理由：

① MySQL 没有和 PostgreSQL 咨询锁等价、并且确定能经过 TDSQL 代理用的机制；② 选主要一直占着一条数据库连接；③ 任务表的去重和租约已经能做到，少一套机制。

⑤ 为什么非这样不可 每条都是「不这样会坏在哪」

1. 为什么领到任务后马上提交，而不是在一个事务里「领取 + 干活」？（第 1 步）

在一个事务里干活：发布要两三分钟，这期间这一行一直锁着，一条数据库连接也一直被占着（后台进程总共才 5–10 条）。等 DSH 的时候开着事务，还违反了「事务里不调用外部系统」的规则。

只锁不改状态就提交：锁一释放，别的进程看到它还是「排队」，又领一次。

所以是：短事务里锁行、改成运行中、提交；然后再干活。之后靠租约证明「我还在做」。

2. 为什么用 SKIP LOCKED，而不是等锁？（第 1、3 步）

等锁：几个进程同时来领，都卡在同一行上排队，前一个提交了，后面的才发现它已经被领走，白等。

跳过：被别人锁着的行直接跳过，去找下一条能领的。领取变成「各领各的」。

3. 已经有「排除更早排队的任务」这条规则了，为什么还要唯一索引？（第 3、6 步）

两条规则管的不是一件事：

排除规则管顺序：同一个串行键下，有更早的任务还在排队，后面的就不领。它只看「排队」的任务。

前一个任务一旦变成「运行中」，就不再挡后面的了（第 3 步的 job_2 就是这样）。如果只有排除规则，job_2 会被领走，和 job_1 同时跑。

唯一索引管「同时只跑一个」：运行中串行键不能重复，第二个想改成运行中，数据库直接拒绝。这一句失败，事务继续去领别的。

4. 为什么要代次？看「持有者是不是我」不行吗？（第 8 步）

同一个进程可能领到同一个任务两次：比如 Worker-1 卡住后租约过期、任务退回排队，恰好又被 Worker-1 自己领走。持有者名字一样，但卡住前那段代码和新领的那段代码是两次不同的执行，按名字分不出来。

代次每领取一次加一，每一次领取都有自己的号码。持有者名字只用来排查问题。

5. 为什么判断「他死了」要等 60 秒，不能快一点？（第 5 步）

一个进程是死了还是只是慢，外面分不出来，唯一的依据是「很久没续租」。

定得太短：网络抖一下、进程停顿几秒，任务就被别人接手，两个进程同时做的情况变多。

60 秒有效、20 秒续一次，中间能容忍两次续租失败。代价是真崩了要等最多 60 秒加一次检查间隔（10 秒）才有人接手。

6. 为什么重跑时不能「从头再来一遍」？（第 7 步）

从头再来：重新组装会生成另一个版本号和另一条发布记录；重新发安装请求，DSH 上可能装两遍。

任务表只记「谁在做」，不记「做到第几步」，旧进程内存里的进度也拿不回来。所以处理器要看业务表里已经留下的东西（发布记录 apr_31 是什么状态），决定从哪接着做；对 DSH 发出去、结果不明的请求，按请求 ID 去查，确认没生效才用同一个 ID 再发（「先落记录再外呼、不盲目重发」那条决定）。

7. 「运行中串行键」是怎么来的？job_1 和 job_2 为什么是同一个值？

串行键是建任务时填的：发布任务的串行键规定为 agent-publish:<Agent ID>（0004 第 3.4 节「按键串行的用法」，依据 0011 第 2 节「同一 Agent 的发布串行」）。job_1、job_2 都是「客服 Agent」的发布，所以串行键相同（页面上用「客服」代替 Agent ID）。

运行中串行键是数据库自动算的，不是谁写进去的。任务表里它是一个计算列：CASE WHEN 状态 = 运行中 THEN 串行键 END，状态是运行中时等于串行键，其他状态都是空；这一列上有唯一索引。

所以 job_1、job_2 并没有「同时用同一个运行中串行键」：job_1 运行中，它的这一列是 agent-publish:客服；job_2 排队，这一列是空（见第 3 步的表）。job_2 想改成运行中时，这一列会变成 agent-publish:客服，和 job_1 重复，唯一索引就拒绝这次修改。空值不算重复，所以排队、已完成的任务再多也不冲突。

8. 代次和尝试次数现在总是一样，为什么不合并成一列？

按现在的 0004，两个数都是「领取时加一」、都不清零，所以值总是相等，合并成一列在技术上完全可以。

RFC 没写为什么分开。组长原版就有这两列，原版只写了尝试次数用于「延迟执行与重试」；现在的写法是「领取时加一」，这样反复把进程搞崩的任务也会耗尽次数，于是两个数变得一样。

真要用到「不一样」，只有一种情况：以后有人想把同一个任务的尝试次数清零重试。但这个需求 RFC 里没有；任务出了问题，取消它、再建一个新任务就行（新任务有新的 ID，代次和尝试次数都从 0 开始）。所以分开不是必须的。

结论：合并、不合并都对。这两列只在框架的任务代码里用，以后想合并，也只改框架代码和一个迁移，不影响各模块，所以不需要现在定。

⑥ 它不保证什么

  • 不保证只执行一次。最长 20 秒里可能两个进程在做同一个任务。处理器的每一步都要能重复。
  • 代次只挡得住任务表的写。旧执行者杀不掉，它已经发给 DSH 的请求也撤不回来；它在发现失去资格之前写的业务数据，也要靠处理器自己做到「重复无害」。
  • 改到 0 行才说明失去资格。数据库连不上、超时，什么也说明不了，不能当成「我已经不是持有者」，也不能当成「我还是」。
  • 不记录任务做到第几步。恢复靠各模块自己的业务表（比如发布记录的状态）。框架不做「保存执行进度」的万能表。
  • 不保证准时。领取约每秒一次；崩溃后最慢要租约 60 秒 + 检查间隔 10 秒才有人接手。
  • 串行键只管「一次一个、按顺序」，不管后一个还该不该做。比如修订号变了要不要返回冲突，是 M04 自己的业务判断。

⑦ 自测 先自己想，再点开

1. Worker-1 在 10:05:20 续租成功，10:05:30 崩溃。这个任务最早什么时候能被别人领走？

租约到 10:06:20。之后某个后台进程的过期检查（每 10 秒一次）把它退回排队，大约在 10:06:20 到 10:06:30 之间；再过约 1 秒被领走。和崩溃时间 10:05:30 无关，只和最后一次续租有关。

2. 同一个 Agent 有 job_A（10:00 提交）和 job_B（10:01 提交）都在排队，没有在跑的。两个后台进程同时来领，结果是什么？

只有 job_A 被领走。job_B 有更早的 job_A 在排队，被排除规则挡住；job_A 变成运行中以后，job_B 再想改成运行中会撞唯一索引。job_B 要等 job_A 结束。

3. 某个任务每次执行都会把进程搞崩。会一直循环下去吗？

不会。尝试次数在领取时就加一，不是做完才加。崩了 → 租约过期 → 退回排队 → 再领（加一）…… 到了上限（默认 5），过期检查不再退回排队，而是标「死信」并告警。

4. Worker-1 卡住后醒来，续租改到 0 行。它该做什么？它卡住前写的发布记录怎么办？

立即停止，不写结果、不再做任何事，因为任务已经被 Worker-2 以代次 2 领走了。它之前（以及醒来后、发现失去资格前）写的业务数据，靠 M04 处理器「重复执行也不出错」来保证无害：Worker-2 会根据发布记录的状态接着做。

5. 两个后台进程都在计划时间给「每日清理」插任务，表里有几条？如果那一刻两个进程都宕机了，恢复后呢？

1 条，去重键 cron:规则名:计划时间 相同，第二次插入撞唯一约束。宕机错过的，恢复后最多补一次，还是 1 条。

出处：0004 第 3.4 节（领取、串行、租约、代次、状态、取消、执行池、定时任务）、第 3.5 节（不选主）、第 3.6 节（任务表的列：运行中串行键、尝试次数上限默认 5、代次）、第 3.7 节第 1、4 条（事务里不外呼、条件更新）、第 2.5 节（后台进程连接池 5–10 条）；0011 第 2 节、第 7.5 节（发布六步、修订号冲突、发布记录状态、串行键 agent-publish:<agentId>）；决定记录「先落记录再外呼，结果不确定只对账不重发」。
示意，不是 RFC 定的：所有时间、ID（job_1、job_2、apr_31、apr_32）、「Worker-1 卡住约 80 秒」、串行键里用「客服」代替 Agent ID、定时规则名。
我的推断，RFC 没写到这么细：第 7 步「重跑时看到已有发布记录就接着做，不再做第 1 步的修订号检查」。0011 只写了「轮到它时修订号变了就返回冲突」，没写被接手重跑时怎么办；按上面的写法，重跑时修订号已经变成 8，如果再检查一次就会把一次本该完成的发布误判成冲突。
