架构级：知道做什么、为什么即可。

九个模块怎么装在一起、怎么防止越界

机制：装配与模块边界（后端框架 0004 第 2.2、2.3、2.5、3.7、10.1 节）。例子：一个模块的开发者犯了几个常见的越界错误，分别在哪一关被拦住。

这一页想让你讲得出：模块之间能怎么调用、不能怎么调用；每种越界由谁拦、在什么时候拦（启动时、CI 时还是只靠评审）；为什么一个库、一个账号、一个连接池。 框架 = 你负责的 0004；M04 = 例子里犯错的模块（发布模块只是举例）。

① 先分清四对词

api 包 ≠ 模块内部

api 包
每个模块对外公开的接口和数据类型。别的模块只能注入这里的接口。
内部
实现类、存储类、处理器……别的模块看不到，也注入不了。
每个模块一个 Spring 配置类，只把 api 包里的接口作为 Bean 暴露出去。

表名前缀 ≠ 独立的库

表名前缀
全平台一个库，模块靠表名区分：identity_users、platform_jobs……
独立的库
每个模块一个库或 schema、各用各的数据库账号。行内建库、建账号要申请，现在只有一个库一个账号，所以不这样做。
隔离靠三样：表名前缀、按前缀分包生成的 jOOQ 类、Spring Modulith 的模块校验。

启动失败 ≠ CI 失败 ≠ 评审

启动失败
进程装配时校验不过，直接起不来，「不带病运行」。
CI 失败
提交代码时自动检查不过，合不进去。
评审
机器查不了，只能靠人看。
验收时要知道每条规则落在哪一关（② 走一遍）。

模块之间调用 ≠ 共享事务

调用
进程内直接调对方 api 包的 Java 接口。
不共享事务
跨模块调用时不得持有打开的事务；每个模块在自己的事务里写自己的表。
所以跨模块要「同时成功」的事，靠事件（A5）而不是一个大事务。

② 走一遍 点「🚫 被拦住时」看结果

③ 模块清单写什么 每个模块一份，任何一项与清单外的约定不一致，进程启动失败

字段内容谁检查
名字、表名前缀模块名、表名前缀jOOQ 按前缀分包；CI 查引用
依赖哪些模块写在模块的 package-info.java 注解里Spring Modulith 校验（允许的依赖、只经 api 包、无环）
要哪些 DSH 分组只能是 RFC-0001 分给它的那几组启动校验
提供哪些契约接口比如会话模块提供 C07以 api 包接口类型暴露为 Bean
要用哪些契约接口只有列出的才能注入；提供方的契约目录里必须把本模块列为使用方评审
路由、tool 回调、事件流引用 OpenAPI 的接口名；处理哪些业务 tool；向浏览器提供哪些事件流启动校验；契约比对进 CI
订阅订阅的事件和处理器；要按顺序的标出来（A7）启动校验
任务、定时规则任务类型和处理器、所属执行池（不写为 default；long 只给框架）、cron 规则启动校验；提交未登记的类型被拒

框架层三处「跨层」用法：DSH 适配层的连接配置来自运维模块、进程令牌来自身份模块，入口验签要查 DSH 适配层的连接登记。它们都由 backend/bootstrap 里的配置类接线，在装配校验里显式登记，不算越界。

④ 为什么这样做 每条都是「不这样会坏在哪」

1. 为什么只准注入 api 包里的接口？

能直接用别的模块的内部类：大家很快就会互相调实现类、直接读写对方的表，模块边界名存实亡；以后想把某个模块拆成独立服务，到处都是要改的地方。

只经 api 包：模块对外只有契约里写的那些接口，内部怎么改都不影响别人；以后拆服务，把接口换成远程调用，调用方不用改（0004 第 2.4 节）。

2. 为什么用 Spring 容器装配，不自己写工厂函数或注入框架？

Spring 本来就在用，容器自带按类型注入、按配置启用组件；Spring Modulith 还能直接按包结构校验模块依赖。自己写一套等于重复造轮子，还要自己维护。

3. 为什么一个库、一个数据库账号？

每个模块一个 schema、两个数据库角色：行内建库、建账号都要申请，目前只有一个库、一个账号。

表名前缀 + jOOQ 按前缀分包 + Modulith 校验，已经能把模块区分开。一个库还带来好处：模块的业务写入和框架的事件登记、幂等记录天然在同一个事务里（A4、A5）。

4. 为什么每个进程只有一个连接池、一个事务管理器？

每个模块一个：三个进程就要 60–150 条连接；多个事务管理器容易「静默写错地方」（以为在一个事务里，其实是两个）；只有一个账号时分开也没有意义。

5. 为什么只留 Modulith 一套依赖检查？

原设计还有依赖清单比对脚本、ArchUnit 使用方检查，三套表达的是同一件事，改一处要改三处。

Modulith 校验已经能拦住越界访问和循环依赖；docs/module-deps.yaml 只作为文档和它保持一致。

⑤ 它不保证什么

  • 「要用哪些契约接口」只靠评审。清单里列了、但提供方没把你列为使用方，机器查不出来。
  • 不拦写原生 SQL。规则是「不写 SQL 字符串，确需原生 SQL 的走评审白名单」，靠评审。
  • 不拦跨模块调用时开着事务。这是规则，没有自动检查，靠评审和测试。
  • 不拦业务上的越权。模块边界管的是「代码能调谁」，「用户能做什么」是判权（A3）。

⑥ 自测 先自己想，再点开

1. 发布模块的代码 import 了会话模块的一个实现类，什么时候会被发现？

Spring Modulith 的模块校验会发现「没经 api 包访问别的模块」，校验失败，进程启动失败（测试里也会跑这个校验）。

2. 发布模块的代码用了 identity_users 的 jOOQ 类去查账号，会怎样？

CI 检查发现模块代码用了别的模块前缀的生成类，CI 失败，合不进去。正确做法是调身份模块 api 包里的接口。

3. 某模块在清单里把一个任务类型的池写成 long，会怎样？

进程启动失败。long 池只给框架自己的任务（跟随器、应答通道）。

4. 为什么说「跨模块要同时成功的事靠事件」？

模块之间不共享事务，没法把两个模块的写入放进一个事务。做法是：本模块在自己的事务里改数据并登记事件，对方在自己的事务里处理事件（A5）。

出处：0004 第 2.2 节（Spring 装配、每模块一个配置类只暴露 api 包、模块清单字段、启动失败、三处跨层用法）、第 2.3 节（平台内核）、第 2.4 节、第 2.5 节（一个库、表名前缀、一个账号、一个连接池、jOOQ 分包 CI 检查、跨模块不持有事务）、第 3.4 节（池的启动校验、未登记类型被拒）、第 3.7 节（数据访问规则）、第 10.1 节、第 11.2 节 F1 验收。
示意，不是 RFC 定的：例子里犯错的是发布模块、具体的类名和代码。
