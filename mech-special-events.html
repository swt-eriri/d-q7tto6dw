两种特殊事件：要排序的，和业务回滚了也要留下的

机制：有序订阅、独立事务的审计（后端框架 0004 第 3.3 节规则 4、5）。例子：旧版本什么时候能卸载；张三越权操作被拒，这条记录要留下。

A5 讲的是普通事件：不保证顺序，和业务同生共死。这一页讲两个例外：什么时候必须按顺序处理、怎么做到；什么时候业务回滚了事件也要留下、怎么做到。 框架 = 你负责的 0004；M01 = 会话（嘉敏）；M04 = Agent 配置与发布（蕴颐）；M07 = 身份（你的 0006）。

① 先分清四对词

普通事件 ≠ 有序事件

普通事件
框架不保证顺序，序号一律填 0。绝大多数事件都是这样。
有序事件
只有订阅时标了「要按顺序」的才排序。目前只有一个：C19 版本引用（发布模块订阅）。
不是「重要的事件才排序」，而是「处理顺序反了会算错」的才排序。

聚合 ID ≠ 事件 ID

事件 ID
每条事件一个，用来去重（收件记录）。
聚合 ID
「这条事件是关于哪个东西的」。顺序只在同一个聚合内保证。C19 的聚合 ID 是执行 ID。
同一次执行的「开始引用」一定先于「释放引用」处理；不同执行之间不管先后。

收件记录 ≠ 游标

收件记录
「这条事件处理过没有」，按事件 ID 去重。
游标
「这个聚合已经按顺序处理到第几条」，每个（监听器, 聚合）一行。
有序订阅两个都用：游标管顺序，收件记录管去重。

同事务发布 ≠ 独立事务发布

同事务（普通）
业务回滚，事件跟着消失。
独立事务（审计专用）
另开一个小事务登记并立刻提交，外面的业务回滚了它还在。
用于「拒绝」「失败」的审计：正因为业务失败了才要记，不能跟着回滚。

③ 为什么这样做 每条都是「不这样会坏在哪」

1. 为什么版本引用的两条事件必须按顺序处理？

发布模块靠这两条事件维护「每个版本有哪些执行还在用」，用来判断旧版本能不能卸载。卸载后 DSH 就不能再恢复引用它的会话了。

顺序反了：先处理「释放」时还没有这条引用，什么都不做；后处理「开始引用」时加了一条，而这条永远不会再被释放。v6 看起来一直有人在用，永远卸不掉。如果实现成「释放时减一」，还可能减成负数，导致还有执行在用时就被卸载。

这两条事件甚至是在不同进程里发的：「开始引用」在请求进程受理时发，「释放」在后台进程写终态时发，两边的监听器并发跑，谁先谁后完全没准。

2. 序号为什么要在执行行的锁下分配？

和 A9 的会话序号同一个道理：先锁住聚合行（执行），在它的计数器上加一当序号，再发布事件，锁持有到提交。同一个聚合的事件提交顺序就等于序号顺序，不会出现「序号 2 先提交、序号 1 后提交」。

3. 游标为什么用「条件更新」，不先锁行再读？

序号 n 的处理写成 UPDATE … SET 最后序号 = n WHERE … AND 最后序号 = n − 1，改到 1 行说明前一条处理过了；改到 0 行说明还没轮到，抛可重试错误，等每分钟的重提再来。

先锁行再读：第一条事件到来时游标行还不存在，锁一个不存在的行会加间隙锁，并发时容易死锁（0004 第 3.6 节）。

4. 审计为什么不能和业务放在同一个事务？

放在一起：越权操作被拒时业务要回滚，审计登记跟着回滚，「谁试图做什么被拒了」就没有记录了，安全上最需要的记录反而最容易丢。登录失败同理。

所以拒绝、失败类的审计用独立的小事务登记：它的聚合 ID 是「发出方:请求 ID」，序号 0，不排序。成功的变更（比如管理员改了角色）的审计照常和业务同事务，改成功了才记。

5. 既然有了引用计数，卸载为什么还要等 24 小时？

有一个空档：会话模块刚解析到旧版本 v6，指针恰好切到 v7，而「开始引用」事件还没到发布模块，卸载检查看到 v6 没人用。宽限期（默认 24 小时）盖住这个空档。卸载条件还包括：不是当前发布版本、没有评估的 hold、不是未退役的试运行版本（0011 第 3 节）。

④ 它不保证什么

  • 只在同一个聚合内保证顺序。不同执行的事件之间不排序。
  • 前一条一直失败，后一条就一直等。序号 1 的处理有 bug，序号 2 每分钟被重提、每次都改到 0 行，1 小时后告警。
  • 只有标了「要按顺序」的订阅才排序，发出方还得真的分配序号。发出方忘了在锁下分配，或者用了别的写法，顺序保证就不成立，而且不会报错。目前只有会话模块发 C19 时要这样做（执行表上有专门的计数列）。
  • 独立事务的审计只记「拒绝、失败」。它不知道外面的业务最后成没成，所以不能拿来记成功的变更。

⑤ 自测 先自己想，再点开

1. 同一个执行的「释放」先被处理到，游标会怎样？这条事件最后怎样？

「释放」序号是 2，条件更新要求「最后序号 = 1」，但游标行还没有（序号 1 没处理），改到 0 行 → 抛可重试错误，登记保持未完成。等「开始引用」处理完（游标变成 1），下一次重提时「释放」就能处理了。

2. 为什么说这两条事件「在不同进程里发」？

「开始引用」在执行受理时发，受理在请求进程里；「释放」在执行进入终态时发，终态是跟随器在后台进程里交给会话模块写的。提交后监听器在提交事务的进程里跑（A5），所以两条事件的处理在两个进程里并发进行。

3. 张三（普通使用者）想保存 Agent 配置被拒了。数据库里留下了什么？

Agent 配置没变（业务回滚）；事件登记表里有一条访问拒绝的审计登记（独立事务已提交），之后由审计模块处理存档。

4. 普通事件（比如 A5 的「Agent 版本已发布」）的序号是多少？

0。只有被「按顺序」订阅的事件才分配序号；序号为 0 的事件不排序。

出处：0004 第 3.3 节规则 4（审计独立事务、聚合 ID、序号 0）、规则 5（顺序、锁下分配、游标的条件更新）、规则 6（重提、1 小时告警）、第 3.6 节（游标表、不先锁再读的原因）；0011 第 3 节（旧版本卸载、引用、卸载条件、宽限期）、第 6.4 节（C19 有序订阅）；0012（C19 发出时机、执行表上的序号计数列：开始引用为 1、释放为 2）；0006 第 8.3 节（访问拒绝、登录失败用独立事务发审计）。
示意，不是 RFC 定的：时间、ID、「开始引用的处理失败了一次」这个情节、游标与引用表里只画了相关的列。
