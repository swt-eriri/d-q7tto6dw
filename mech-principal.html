「这是谁」和「能不能做」：主体、角色、能力

机制：主体与判权（身份与权限 0006 第 1.1、2.2、2.3 节）。例子：张三想导出数据；王经理发起的自进化评估跑到一半，他被降级了；李四被重置密码后，CRM 还在替他调用。

这一页想让你讲得出：四种主体各是什么、凭什么进门；为什么判能力不判角色；后台任务按谁的能力判、为什么按「当前」；「必须改密」在网页和接入应用下为什么不同；显示菜单和执行操作为什么用两个接口。 M07 = 身份与权限，你负责的 0006；框架 = 你负责的 0004；M06 = 自进化（闻洛）；业务模块 = 调判权接口的各个模块。

① 先分清四对词

凭证 ≠ 主体

凭证
拿来进门的东西：登录 cookie、应用凭据 + 声明的实际用户、任务记录、进程令牌。
主体
进门后平台内部只认的「这是谁」，四种：用户、接入应用 + 实际用户、评估账号、服务（后台任务）。
判权一律针对主体，不针对凭证（A3）。

角色 ≠ 能力

角色
两种：使用者、全站管理员。是账号上的一列。
能力
能做的具体事情：对话、Agent 配置与发布、账号管理……各模块和前端只看能力，不看角色。
角色到能力的对应是代码里的一张固定表，不建表。

显示用 ≠ 执行用

getCapabilities
给页面决定显示哪些菜单、按钮。不留审计。
checkCapability
真要执行操作前调。每次按主键查一次账号、不缓存；拒绝时身份模块统一发一条访问拒绝审计。
用 checkCapability 判断显示，会产生大量无意义的拒绝审计。

发起人「当时」的能力 ≠「当前」的能力

当时
发起任务那一刻他是管理员。
当前
后台任务每次判权都按发起人此刻的能力判。他被降级、停用了，任务后续的判权一律拒绝。
后台任务不会「带着旧权限一直跑下去」。

② 走一遍 有按钮的步骤可以看「被拒时」

④ 为什么这样做 每条都是「不这样会坏在哪」

1. 为什么判能力，不判角色？

各模块判角色（「是管理员才能发布」）：以后加一种角色（比如「Agent 运营」），要改所有模块和前端。

判能力：加角色只改代码里那一张对应表，其他模块和前端不用动。代价只是多一个枚举。

2. 数据导出为什么不跟角色走？

需求（OH-IAM-F008）要求按人授予「允许数据导出」，管理员也不自动拥有。导出的是业务数据，和「能不能管理平台」是两回事。

3. 后台任务为什么按发起人「当前」的能力判？（第 5 步）

按发起时的能力：王经理被降级甚至离职停用后，他之前发起的自进化还能带着管理员权限继续改 Agent、跑评估。

按当前：每次判权都查他此刻的账号。降级后任务的下一次判权就被拒（原因「没有这项能力」），停用的原因是「账号已停用」，没有发起人的是「没有发起人」。

4. 「必须改密」为什么只拦网页，不拦接入应用替他调用？（第 6 步）

网页登录时能力清单为空，改密前所有判权自然被拒，不用另写拦截。

如果接入应用替他调用也这样：只在业务系统里用平台、从不登录网页的人，每次开放 API 调用都会被拒，而且看不出原因。应用调用也用不到他的密码。

5. 判权为什么不缓存？

角色变了要立刻生效。每次按主键查一次账号，代价很小。入口的认证缓存 30 秒只管「这个 cookie 是谁」，不影响判权（A3）。

⑤ 它不保证什么

  • 只管「有没有这项能力」，不管「这个对象是不是他的」。会话是不是张三的、某个 Agent 有没有对他开放，是各模块自己的对象授权。
  • 不管数据范围。能查哪些数据由取数网关按 uid 判断，管理员角色不扩大取数权限（B4）。
  • 模块不调 checkCapability 就没有判权。入口只认证不授权（A3），漏调只能靠评审和测试。
  • 已经在跑的东西不会因为降级而立刻停下。它只是在下一次判权时被拒；进行中的 DSH 执行怎么处理，按会话模块的规则（B6）。

⑥ 自测 先自己想，再点开

1. 全站管理员王经理能导出数据吗？

不一定。导出只看账号的「允许数据导出」，管理员也不自动拥有。

2. 前端用 checkCapability 来决定是否显示「发布」按钮，有什么问题？

每次打开页面、每个没权限的人都会产生一条访问拒绝审计，审计里全是噪音。显示用 getCapabilities。

3. 王经理发起评估后被停用了，评估后续的判权返回什么原因？

拒绝，原因「账号已停用」（停用或移除都是这个）。降级是「没有这项能力」。

4. 打分会话（平台服务主体）调 checkCapability 会怎样？

一律拒绝，原因「没有发起人」。它能做什么，由它的进程令牌种类限定（B5）。

5. 以后要加一个「Agent 运营」角色（能发布 Agent，不能管账号），要改哪里？

只改身份模块代码里的角色→能力对应表（和角色枚举）。各模块、前端看的都是能力，不用改。

出处：0006 第 1.1 节（四种主体与凭证）、第 2.2 节（角色到能力、导出按人授予、必须改密）、第 2.3 节（判权规则、拒绝原因、显示与执行用不同接口）、第 8.1 节（getCapabilities、checkCapability、DecisionReason）、第 8.3 节（访问拒绝审计）、第 10.1 节；0004 第 3.1 节（服务主体由框架按任务记录构造）。
示意，不是 RFC 定的：时间、ID、评估的具体步骤、M06 被拒后怎么收尾。
